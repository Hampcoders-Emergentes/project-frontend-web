# Known limitations (verified against the code)

Severity: 🔴 blocks a documented feature · 🟠 surprising/risky behaviour · 🟡 caveat.

## Real-time and integrations

| # | | Limitation | Evidence | Frontend workaround |
|---|---|---|---|
| 1 | 🟡 | **Email is log-only without SMTP.** `LoggingEmailSender` is registered when `Email:Smtp:Host` is empty: password-reset and alert emails are not delivered but the API answers 200. Now detectable: `GET /api/v1/notification-channels` reports `EMAIL` as `LOG_ONLY` / `configured: false`. | `EmailServiceCollectionExtensions`, `NotificationChannelReadinessAdapter` | Read `GET /notification-channels` and warn before routing alerts to a `LOG_ONLY` channel. |
| 2 | 🟡 | **SMS is log-only without a gateway.** `LoggingSmsAlertChannel` writes to the log (masked) unless `Notifications:Sms:GatewayUrl` is set. Reported as `LOG_ONLY` by `GET /api/v1/notification-channels`. | `StoreManagement/Infrastructure/Configuration/WebApplicationBuilderExtensions.cs`, `ExternalAlertChannels.cs` | Hide or flag SMS routes when the endpoint says `LOG_ONLY`. |
| 3 | 🟠 | **`disabled` providers fabricate data.** `ExternalProviders:Payment=disabled` returns fake customers/portal URLs (`?portal=null`); `FileStorage=disabled` returns `https://null-storage.local/...`; `AIMatching=disabled` yields no candidates (deterministic matching only). Docker Compose ships all three disabled. | `Shared/Infrastructure/ExternalProviders/Null*.cs`, `docker-compose.yml` | Treat Compose as non-functional for payments/uploads. |
| 4 | 🔴 | **Direct Cloudinary upload for property and work photos cannot be reproduced client-side.** The API signs `folder`, `allowed_formats`, `max_bytes` and `timestamp` but returns only `url`, `signature`, `timestamp`, `apiKey`; the property/work folders embed a server-side `yyyyMMddHHmmss` the client cannot know. Profile photos are deterministic and work. | `FileStorageService.cs`, `CloudinaryFileStorageProvider.GetSignedUploadUrlAsync` | Request backend change (return signed params) before building those screens. |
| 5 | 🟠 | **Device onboarding AI has no fallback** (Groq URL hard-coded; failure → 503). | `DeviceOnboardingService.cs` | Show retry/manual threshold entry (`PUT /profiles/{profileId}/thresholds`). |
| 6 | 🟡 | **MQTT broker in Docker is anonymous/no TLS**; if the broker is down relay commands are silently not delivered (REST still returns 204). | `docker/mosquitto/mosquitto.conf`, `MqttDeviceSubscriberService.PublishCommandAsync` | Poll relay history; show `Pending/Timeout`. |
| 7 | 🟡 | **TS04 asks for a dedicated microservice; reports are generated in the monolith**, synchronously. A second request for the same report (same caller and store) while one is running gets `409 REPORT_IN_PROGRESS`; the guard is in-memory, per API instance. | `ComplianceAssessmentService`, `EnergyReportCommandService`, `ReportGenerationGuard` | Allow several seconds for large ranges; disable the button while waiting; no progress API. |

## Security / operations

| # | | Limitation |
|---|---|
| 8 | 🟠 **Edge API key is a single shared secret** for all gateways. In **Development** `appsettings.Development.json` now sets `EdgeApi:ApiKey=dev-edge-key` and allow-lists `dev-001`, `dev-002`, `dev-003`, `prop-demo` for `EquipmentReadings` and `RelayHistory`. Outside Development the lists default to empty ⇒ **403 for every edge request** (startup warning); Docker Compose defaults the key to `dev-edge-key`. |
| 9 | 🟠 `ForwardedHeaders` trusts any proxy (known proxies/networks cleared) and `AllowedHosts` is `*`; the contact-form limiter keys on the (spoofable) forwarded IP. |
| 10 | 🟡 HTTPS redirection runs only in Development; TLS must be terminated upstream. |
| 11 | 🟡 Global throttling is in place (fixed window per user id, per IP when anonymous; defaults 300 / 60 requests per 60 s, `RateLimiting:*`), with `Retry-After` and `errorCode: RATE_LIMITED` on every 429. Counters are **in-memory per API instance** (a scaled-out deployment multiplies the effective limit), anonymous partitions key on the forwarded IP (see 9), and edge/webhook routes (`/iot/edge`, `/alerts/dispatch`, `/webhooks`) are exempt. |
| 12 | 🟡 Audit logging uses a bounded in-memory queue (10 000) that **drops** entries when full; reads are not logged unless `Audit:IncludeReads`. |
| 13 | 🟡 Schema: `AppDbContext.EnsureCreated()` only acts on an *empty* database and never evolves it; only the StoreManagement context has real migrations. Production schema changes need a separate deployment step (`Database:MigrateOnStartup=false`). |
| 14 | 🟡 CORS origins are configuration only: `Cors:AllowedOrigins` lists `http://localhost:4200` (Angular) and `http://localhost:8081` (Docker prod web) in `appsettings.json` and `appsettings.Development.json`; deployments add their domains with `Cors:AdditionalOrigins` (comma/semicolon separated, e.g. env `Cors__AdditionalOrigins=https://<vercel-prod-domain>,https://<vercel-preview-domain>`). Wildcards are not supported: each Vercel preview URL must be listed (a `*.vercel.app` rule would let any Vercel app send credentialed requests). Origins must be `scheme://host[:port]` (startup fails otherwise; `*` is rejected). `PasswordReset:FrontendUrl` and the Stripe URLs still point to `:4200`. The committed `appsettings.json` holds non-secret Stripe price ids; keep secrets in environment variables. |
| 15 | 🟡 Wear predictions need 30 running samples per equipment and period comparisons 2 samples per period. Both responses now say so explicitly (`dataQuality: SUFFICIENT \| INSUFFICIENT_DATA`, `sampleCount`, `minimumSamples`, plus `equipmentDataQuality` on predictions); with `INSUFFICIENT_DATA` an empty prediction list or a zero/±100% change is "cannot tell", not "healthy". |
| 16 | 🟡 Alerts: one alert per reading (no incident grouping, hysteresis or re-open); `Open` alerts can pile up during sustained anomalies. |
| 17 | 🟡 `SubscriptionEligibilityResource` and several `*Internal*`/`Create*` subscription resources exist in the code but are **not exposed** by any controller (documented schemas intentionally omit them). |
| 18 | 🟡 Alert change sequences (`sequence`, `GET .../alerts/changes`) start with the migration `AddAlertChangeSequence`: alerts last changed before it have `sequence: 0` and only appear in the full lists. Acknowledge/assign/resolve are sequenced but **not pushed** over SignalR (only new alerts are) — poll `alerts/changes` to see them live. |
| 19 | 🟡 Error contract: `errors` values are now field **codes** (`REQUIRED`, `INVALID_FORMAT`…); the previous English texts moved to `errorMessages`. Clients that rendered `errors` text directly must switch to translating codes (or read `errorMessages`). Model-validation keys keep their C# / JSON-path spelling (`Name`, `$.ownerUserId`); IAM field errors use camelCase request members (`email`, `passwordConfirmation`). |
